2. Dual Panel Architecture

Admin Panel — /admin
Who: Developer / Site admin
Full PostResource CRUD
PostCategoryResource with component picker
User / Role management
CrmSettings (full config)
AI: Generate Site / Components
Service Payments
Activity log / Exceptions
Unchanged from v1 — same power, same flexibility
Client Panel — /dashboard
Who: Business owner / Client
📄 أقسام الموقع — Section cards + Edit
📝 الصفحات — Simple page editor
💬 الرسائل — Contact entries (read-only)
⚙️ الإعدادات — Phone, email, social, logo
👤 حسابي — Profile settings
Simplified — only what client needs to edit
Key: Both panels read/write the SAME database tables. No data duplication. Client panel is a filtered, simplified view of the same data the admin sees.

3. Data Layer — Zero Schema Changes

Existing models power everything — no migrations needed for v2 core
PostCategory
= Section header
section_component → component key
name → section title (translatable)
description → subtitle (translatable)
order → sort position
is_active → visibility toggle
Post
= Section item
post_category_id → belongs to section
title → item title (translatable)
content → item body (translatable)
metadata → extra fields (JSON, translatable)
image_id → item image
order → sort within section
CrmSetting
= Site-wide config
key → setting name
value → setting value (JSON cast)
Used for: phone, email, logo,
social links, business info,
theme colors, etc.
// The magic — metadata JSON stores ANY extra fields
Post::create([
  'title' => ['ar' => 'تصميم مواقع', 'en' => 'Web Design'],
  'content' => ['ar' => 'نصمم...', 'en' => 'We design...'],
  'metadata' => [
    'icon' => 'heroicon-o-globe', // ServicesComponent field
    'price' => '500', // PricesComponent field
    'cta_url' => '/contact', // Any component's field
    'rating' => 5, // ReviewsComponent field
  ],
]);

What's new in v2 API:
  • Sections endpoint returns component-typed data
  • Each section includes its component key
  • Angular frontend uses component key to render
  • fields object = component-specific extras from metadata
  • Backward compatible: v1 routes still work
API Routes:
GET /api/v2/sections — all sections
GET /api/v2/sections/{id} — one section
GET /api/v2/settings — site settings
GET /api/v2/pages/{slug} — page by slug
GET /api/v2/menus — navigation
POST /api/v2/contact — submit form
GET /api/v2/components — available types

6. Extensibility Points

🔌 Custom Components
Developer adds a PHP class
implementing SectionComponent.
Auto-discovered. Shows up in
admin component picker + client editor.
🎨 Custom Field Types
FieldFactory is extensible.
Add new field types via config
or ServiceProvider. Used in
component editSchema().
🔄 Custom API Transforms
Each component's toApi() controls
its JSON shape. Override for
any format Angular/React needs.
🛡️ Auth & Middleware
Panels use Filament's built-in
auth. Client panel gets own guard.
Config-driven middleware stack.
🌐 Locale Strategy
Arabic-first. All translatable
fields default to AR. EN optional.
Config: crm.locales = ['ar','en'].
📦 Theme / Blade Override
Components point to blade views.
Laravel view override: publish &
customize any template per-project.

Migration Path from v1 → v2

Step 1
Upgrade Filament 3 → 5 (follow Filament upgrade guide)
Step 2
Existing admin panel moves to Filament/Admin/ namespace — no functionality change
Step 3
Component classes created for each existing blade template (1:1 mapping)
Step 4
Client panel added — reads same DB, no data migration needed
Step 5
API v2 routes added alongside v1 (v1 stays for backward compat)
